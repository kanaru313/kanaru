# System architecture: lyrics plugins

Part of [System architecture](system-architecture.md).

### Plugin runtime

Lyrics plugins are JavaScript (`search.js`, `lyrics.js`) run by a sandboxed QuickJS-NG engine in the Rust crate (`rust/src/plugin_runtime/`, bridged by `api/plugin_runtime.rs`; contract and limits in [lyrics-plugin-api.md](./lyrics-plugin-api.md)). Dart reaches it through `lib/core/plugin_runtime/`: `PluginRuntime` (`run`, `check`), `RustPluginRuntime` (the only file that imports the generated bindings) and `pluginRuntimeProvider` (no dependencies). `core/plugin_runtime` is generic and imports nothing from `core/lyrics`; the lyrics host maps its results to `LyricsFetchKind`. The wrapper begins a job per run, forwards `PluginCancel` to `cancel_plugin_job` (a token cancelled before the run still goes through Rust, which frees the id), answers a throwing fetcher as `network`, and returns a failed bridge call as status `internal` (details in [lyrics-plugin-api.md](./lyrics-plugin-api.md#dart-api)). Rust unit and integration tests inject a Rust closure instead of the Dart callback; `test/core/plugin_runtime/` has pure mapping tests plus a `native`-tagged test that loads the cargo-built debug library (skipped when it is missing).

| Part | How it works | Where |
|---|---|---|
| Threads | A pool of 4 `plugin-js` threads (8 MiB stack each) and a queue of 16; the 17th waiting job is `Busy` (the caller skips that source for the lookup). `run_plugin_script` is an `async` bridge function that only queues the job and awaits a one-shot, so no bridge worker or Dart isolate blocks | `pool.rs`, `mod.rs` |
| Per call | A fresh `Runtime` and `Context` on the worker, dropped on the same thread; nothing is shared between calls (about 1 ms with a trivial script, measured; the budget is 5 ms) | `engine.rs` |
| Limits | Heap 32 MiB (a counting allocator sets a flag when it refuses memory), JS stack 1 MiB, 15 s wall time, 2 MiB of output. The interrupt handler (cancel flag or deadline) is uncatchable by the script; the stack error comes from the engine | `limits.rs`, `memory.rs`, `engine.rs` |
| Scripts | Classic global sloppy-mode scripts. `load()` reaches only files of the request; no `std`, `os`, module `import`, `require`, timers or Promise job queue. `execute(input)` must return `Response.success/error` | `globals.rs` |
| Job ids | `begin_plugin_job` registers a cancel flag; cancelling a job that has not started removes it, so a later run is `Cancelled` at once | `jobs.rs` |
| Failures | A panic in a job is caught and ends as `Internal`; the next job still runs. Console lines, the first fetch failure and the JS error (message and stack) are returned on every status, because a per-job collector outlives the failing script | `collector.rs`, `engine.rs` |
| Host API | `fetch`, `sleep`, `localConfig`, `localStorage`, `console`/`Log`, `Html.parse` (Rust `scraper` arena, handles are private fields) and `load('crypto.js')` (bundled CryptoJS 4.2.0). Rust natives are handed to a script-side prelude (`js/host_prelude.js`) that shapes them into response objects and named errors; the natives are never globals | `host*.rs`, `js/` |
| Syntax check | `check_plugin_script` compiles without running (`JS_Eval` with the compile-only flag) on a thread of its own | `compile_check.rs` |

**Fetch callback flow.** `run_plugin_script(request, fetch)` takes a Dart callback. When a script calls `fetch(url, options)`, the JS worker (never a bridge worker or the Dart isolate) builds a `PluginFetchRequest` (method, URL with encoded queries, headers, body, `deadline_ms`, and `max_sends`: the HTTP sends still allowed for the call, 10 minus those used, which Dart must not exceed, retries included) and calls the callback, which returns a future. The worker polls that future itself and parks the thread between polls: it wakes when Dart replies, and every 50 ms to look at the cancel flag and the job deadline. Dart's reply (`PluginFetchResponse`: outcome, status, url, headers, body, `sends`) wakes the worker, which turns it into a response object or a named error. If the job is cancelled or its time ends first, the worker stops waiting and the run ends `cancelled` / `timeout`, even if the script catches the error that unwinds it. Dart is not told: the bridge does nothing when a future is dropped, and a late reply to a dropped future would make the bridge print the whole encoded response. So the unfinished future is never dropped on the JS thread; it goes to one `plugin-late-answers` thread that polls it until Dart replies and discards the answer silently (at most 256 futures, each for at most 120 s; beyond that a future is leaked, not dropped). A callback that throws makes the bridge code panic inside the future; the worker catches that (panic text neither kept nor printed) and answers `network`. The runtime knows nothing about hosts, consent or `LyricsHttp`: Dart decides the outcome. Rust itself checks only the method and the 256 KiB request body, counts the sends Dart reports (10 per call; a report above `max_sends` is clamped), and charges unread response bodies to a 16 MiB Rust-side budget kept in the host environment, so other holders can share it (QuickJS' heap cap does not see Rust allocations; an overrun makes the call `memory` even if the script catches the error); the first failing outcome is kept as `fetch_failure` even when the script catches the error.

### Plugin repository fetch

`RepoHttp` (`lib/core/lyrics/plugins/repo/repo_http.dart`) is the only network path of the repository feature: GET of a catalog, a plugin zip or an icon. It is not `LyricsHttp`: it sends no song data and is not behind the lyrics consent. Each call makes its own `HttpClient`, with the app `User-Agent`, no proxy, a 10 s connect timeout and 20 s for the whole call (all hops), and closes it at the end. When the 20 s pass, no lookup, dial or request starts any more and sockets in flight are destroyed.

1. **Shape**: the URL must be absolute `http` or `https` with a host and no user info; checked before any lookup.
2. **Pinned connection** (`lyrics_http_pinned_connect.dart`): the client's `connectionFactory` resolves the host **once** (an IP literal is not looked up), hands every address of that answer to the repository rules (`repo_address_rules.dart`: class of each address from `lyrics_http_address_class.dart`, mixed answers refused, `http` only for local destinations, a public catalog never reaching a local address or `http`), and then connects to those addresses only (IPv4 first, one after the other, each dial getting an equal share of the 10 s connect budget; a cancelled connection stops dialing). A second DNS answer is never used, which closes DNS rebinding.
3. **TLS** runs on the connected socket with the original host name (`SecureSocket.secure(socket, host: name)`), so SNI and certificate checks use the name, not the IP. No bad-certificate callback exists; an untrusted or mismatched certificate is `network`. Tests inject a `SecurityContext` that trusts a test certificate.
4. **Redirects** are followed by hand, at most 3 (the fourth is `network`). Every hop is checked again with the kind (local or public) of the catalog, which narrows to public once any hop is public, for a catalog, a zip and an icon alike (a public host in the middle of a chain cannot send the request on to the local network), and uses a fresh connection (`persistentConnection = false`), so a reused keep-alive socket cannot skip the check.
5. **Caps**: catalog 1 MiB, zip 5 MiB, icon 64 KiB, enforced on the declared length and on the bytes read; reading stops at the cap. Icons then go through `pluginIconProblem`.

The same pinned factory, in its public-only form (`lyricsPublicOnlyConnectionFactory`), is set on the shared `lyricsHttpClientProvider` client, so LRCLIB and plugin `fetch` also refuse any host name that resolves to a non-public address: `LyricsBlockedAddressException`, which the send loop turns into `LyricsFetchKind.blockedHost` (the plugin sees `BlockedHostError`; `PluginFetchBridge` marks the call `blocked`). When `HttpClient` uses a proxy (from the environment) the proxy resolves the name, so the factory looks the name up locally first (3 s limit) and refuses when that answer is not public; if the local lookup fails it connects to the proxy as configured. On a network that reaches only the proxy and where DNS hangs rather than fails, that pre-check can add up to 3 s to every new connection (accepted; connections are not reused across requests of different hosts). The repository client never uses a proxy: it ignores `HTTP_PROXY`/`HTTPS_PROXY` and connects directly (`findProxy` is `DIRECT`), because the destination must be checked here and not by a proxy. Known limitation: on a proxy-only network without a TUN device, repositories cannot be added or refreshed.

### Plugin repositories: add, refresh, install, update

`LyricsPluginReposController` (`lib/core/lyrics/plugins/repo/lyrics_plugin_repos_controller.dart`) is the API the store UI calls; it holds no UI text (failures are enums). A repository is a row of `lyrics_plugin_repos` keyed by its normalized URL (lower-case scheme and host, no default port, no fragment; the path stays as typed, so the address that is fetched is the one the user typed, except that a bare root `/` is dropped; `repo_url.dart`). The catalog is stored as the checked entries with absolute `path`/`icon` (an address over 2 048 characters once absolute drops its entry, or its icon, at fetch time, so fetch and read-back agree) plus the address class (`local`/`public`) of the fetch (`plugin_repo.dart`); it is read back without any lookup, and the class is recomputed on every refresh. A decoded catalog is kept per repository while its stored text is unchanged (`PluginRepoReader`), so a write to one repository does not parse every catalog again. `last_error` holds the error kind only; the reason of a refused address is kept in memory for the session.

**Class at install, update and icon time.** The zip (and an icon) obeys the stricter of the stored class and a fresh look at the repository URL (`RepoHttp.effectiveKind`, with the client's own resolver): the stored class holds the redirect narrowing, the fresh one catches a name that has since started to resolve elsewhere. It fails closed: a lookup that fails is `download` / `network`, a refused address is `download` / `blockedAddress` with the reason; the stored class is never used alone. Known limit: an IP literal or a `.lan` name counts as local on any network, because nothing tells a foreign network from the user's own.

| Flow | Steps |
|---|---|
| Add | normalize, refuse a known URL (`duplicate`, no request), fetch and parse once, insert the repo (name and author from the catalog) and its catalog (a failure after the insert removes the row again); failures are `AddRepoFailure` (invalid URL, public needs https, network, not found, bad format, other address rule). Result carries the repo name and the entry count |
| Refresh all | every repo, at most 4 at once; stores the catalog and clears `last_error`, or only `last_error` so the old catalog stays (`last_error` stores the error kind only; the reason of a refused address is kept in memory for the session). A call during a running refresh shares it; `refresh(url)` does the same for one repo and shares a fetch of that URL already running (null when the repo is not added, being added or removed meanwhile). A repo removed meanwhile or being added is left out, and it never throws. Two `add` calls for one address at the same time share one run; a repo removed while it is being added is `storage`. Nothing runs on a timer: the UI calls it when the store opens and on "Refresh all" |
| Remove | deletes the repo row only; installed plugins stay and only lose updates |
| Install | the entry comes from the stored catalog; the zip is fetched with the repo's class, read by `PluginPackageReader` (the checks of a file install), and its manifest must match the entry: `version` equal and `hosts` equal as sets, else `catalogMismatch` and nothing is written. Then `LyricsPluginsController.installPackage` with source `repo` (installed data always comes from the zip manifest). A removed record of the same `(url, slug)` is revived under its old id. The result says what happened (`RepoPluginChange`: `installed`, `revived`, `updated`); a live plugin is updated, and Undo (`undoInstall`) is for `installed` and `revived` only, since undoing an `updated` result would uninstall the plugin the user already had. One run per `(repo, slug)`: a second install of it shares the running one |
| Update | `availableUpdate`: live repo plugin, repo still added, catalog `version` above installed, `apiVersion` supported. Same download, read and compare, then `updatePackage`; no consent prompt. Update all runs one plugin after the other, reports each outcome on `updateOutcomes` and `updating` lists the ids in flight (`updatingChanges` emits the whole set on each change and ends empty, also for skipped or failed plugins); install and update of one plugin share one run: an install that finds a live record of the same repo and slug uses the update's run and shows in `updating`; one run per install id, an update during update all shares it, and two update-all calls share one run. File plugins never update. No error escapes install or update: a package that differs from its catalog entry is `catalogMismatch` with `packageDeclared` (the package's own version and hosts) for the dialog; a database or disk failure is `RepoPluginFailure.storage` (logged by type only) and update all goes on with the next plugin |

`plugin_store_view.dart` turns (records, repos with last catalogs, search text, source filter) into the store sections: updates, installed (repo and file plugins), not installed (catalog entries not installed by `(repo url, slug)`, removed records included), the count of entries that need a newer Kanaru, and the repos whose last fetch failed. `PluginStoreInput.available` is false while the plugin feature has no library or data folder (the lists are then empty because nothing can be read). `RepoIconCache` fetches catalog icons on demand and keeps the checked PNG bytes in memory, at most 8 MiB with the least recently used dropped first; a definitive failure (not a PNG, too large, refused, not found) is remembered, a network failure for 60 s or until `clearFailures()`.

### Plugin install, update and uninstall

`LyricsPluginsController` (`lib/core/lyrics/plugins/lyrics_plugins_controller.dart`) is the API the UI calls; the work is split over `lib/core/lyrics/plugins/store/` (dirs, installer, uninstaller, config store, secret cache). Every change (install, update, uninstall, enable, reorder, config, clear) runs through one serial async queue, so an undo, an update and an uninstall never interleave. Reading and checking a zip happen before the queue and write nothing. No core code holds UI text: a refused package is a `PluginPackageProblem` kind.

**Package folders.** Packages live under `<data>/plugins/lyrics/<installId>/v<version>-<time>/` (`plugin.json` regenerated from the checked manifest, `icon.png` when kept, `src/*.js`; every file flushed). `lyrics_plugins.package_dir` holds the relative path of the current one. A folder is written whole before the database points at it and deleted after the database stopped pointing at it, so the database never names a missing or half-written package. File modes come from the process umask (typically 0644 files, 0755 folders). `installId` is `plugin-` plus 12 characters of `[a-z0-9]` from `Random.secure()`, checked against every record.

| Flow | Steps |
|---|---|
| Install | write the new folder; one transaction inserts the record and an empty data row (a repo plugin whose `(repo_url, slug)` has a removed record is revived under the same id: all secrets of its old form are deleted first, config and storage reset; if the secret store cannot delete them the install is refused as `PluginInstallSecretsUnavailable` and nothing changes); then a preference row (on, last). A database failure deletes the new folder and rethrows. Consent flags are not touched. A repo plugin whose record is live is updated instead |
| Update | repo plugins only, version not lower than installed (else `PluginInstallRefused`); block new runs of the plugin (`PluginRunRegistry.block`: `register` returns null) and cancel running ones (`cancelAll`, waits at most 1 s); write the new folder; `switchLyricsPluginPackage` changes `package_dir`, version, hosts, form and `updated_at` in one transaction; delete the old folder; then move config to the new form (`text` to `secret` moves the value into the secret store, `secret` to `text` or a removed key deletes the store entry, values that no longer fit the field are dropped) |
| Uninstall | block new runs and cancel running ones (the block is lifted when the change ends; later runs see a removed or missing record); `uninstallLyricsPlugin` (one transaction); delete the secrets of the old form's secret keys; delete `<installId>/` and `<data>/plugin-logs/<installId>.jsonl*`. A failure after the database step is logged (error type only) and does not undo it. `missing` and `alreadyRemoved` touch nothing. Undo of an install is an uninstall |
| Startup sweep | first job of the controller's queue, so it runs when the controller is first used (the first plugin run or plugin screen), not at app start: deletes every folder under the root that no live record references (a symlink is removed as a link), and log files of ids with no live record |

A crash between writing a folder and the database step leaves an unreferenced folder; after the switch commit it leaves the old one. In both cases the database and the folder it names stay in step and the sweep cleans up.

**What an uninstall keeps.**

| Data | After uninstall |
|---|---|
| Saved lyrics (`found` rows), pins, rejects | kept; the record stays, marked `removed_at`, as their name. Deleted outright when none exist |
| `not_found` rows, config values, localStorage, source preference | deleted |
| Secrets (`lyrics_plugin.<installId>.<key>`) | deleted |
| Package folders and log files | deleted |

**Secrets.** A config field `input` with format `secret` is written only to the `SecretStore` under `lyrics_plugin.<installId>.<key>`; the database, `settings.json` and the logs never hold a value. Values are cached in memory after the first read or write (a keyring call can block the UI thread); concurrent first reads share one call, and a read that began before a write or delete never overwrites it. A failed delete leaves the cache as it was and is reported to the caller. A locked or absent store makes a secret read as empty with one warning per session, and is asked again after a minute. `configForRun` merges stored non-secret values, field defaults and secrets, all as strings. The UI can tell that secrets sit in a plain file or in memory through `secretsUsingFallback()`.

Shared pieces: the route table is `lib/features/lyrics_plugin_store/lyrics_plugin_store_routes.dart` (mounted under the sources route by the router); the store's rows come from `lib/core/lyrics/plugins/repo/plugin_store_view.dart` (pure: records, repos with their last catalogs, search text and source filter to sections); `lyrics_plugin_repos_provider.dart` supplies the repository and catalog streams; failure text is mapped in the UI, so core holds no UI text: package problems, install outcomes, repository install failures and download reasons live in `lib/shared/lyrics_plugins/` (`plugin_problem_text.dart`, `plugin_failure_text.dart`) and are used by both the store and the Sources page; only repository load and add-address text stays in `lib/features/lyrics_plugin_store/repo_error_text.dart`.

### Plugin lyrics provider and source list

**Data flow of a lookup.** `lyricsSourcesProvider` (`lib/core/lyrics/plugins/lyrics_sources_provider.dart`) combines `watchLyricsPluginRecords` and `watchLyricsSourcePrefs` into the ordered list `{id, enabled, position, record?}` (`orderLyricsSources`): LRCLIB (no row: on, position 0) and every live plugin; a plugin without a preference row is on and goes after every saved position, in install order; removed records are not sources. `lyricsSourcesInputProvider` emits for the first time only after both tables answered and again only when a row changed, and `lyricsSourcesLoadedProvider` is true from that first emit on. Until then lookups wait (`whenLyricsSourcesLoaded`), the cache stream stays loading and the resolution reads, so a cached plugin `found` row on a cold start causes no request. `lyricsProvidersProvider` (`lyrics_provider_registry.dart`) is the enabled entries in order, each turned into a `LyricsProviderRegistration` (a plugin becomes a `PluginLyricsProvider`; one whose registration throws, for example a hand-edited host, is skipped and logged by id and reason; without the data folder or database no plugin is registered). `lyricsSourceNamesProvider` names the enabled sources and every plugin record (installed, on or off, `removed: false`; removed, `removed: true`; with its author), so a disabled or uninstalled plugin's saved lyrics still show. A lookup then runs `runOnlineLyricsLookup` per source: `lookup` (a plugin answers `null` without running JS), `search` (`search.js`), the host's match gate, `fetch` (`lyrics.js`) for the best body-less matches, and a row saved under the plugin's `installId`. "Not found" needs every enabled source to have missed, so a newly installed plugin is asked even when LRCLIB already missed.

**One run** (`PluginScriptRunner`, `plugin_script_runner.dart`; the provider is only the input and output mapping):

1. `PluginRunRegistry.register(installId, cancel)` comes first; a blocked plugin (an update or uninstall is changing it) returns null and the run is skipped. Then the record is read; a missing or removed record is skipped too (`LyricsSourceSkipped`: no failure, no pause, no row; the lookup asks that source again next time, see below).
2. Both scripts and every other file of `src/` are read from `<data>/plugins/lyrics/<package_dir>/` once per folder and kept (`PluginPackageLoader`; the entry names come from `plugin.json`; a failed read is not cached). A missing or unreadable folder, a malformed `package_dir`, a bad manifest, or a failure reading the settings, secrets or stored map (typed `PluginRunSetupException`, logged without values) is an `invalidResponse` failure, never "not found".
3. Input: `{title, artist, album, durationMs}` or `{text}` for `search.js`, the result's `id` for `lyrics.js`; `config` from `configForRun`; `storage` from `lyrics_plugin_data`. Each `fetch` of the script goes through `PluginFetchBridge` on the lookup's own `LyricsHttp` (host allowlist, consent, retries, abandon and the `max_sends` cap of the call as for every source). An abandoned lookup ends at the next send, so the run ends cancelled.
4. An outer deadline of 60 s, which also covers loading the package, settings and storage (the runtime's 15 s of script time, which starts only when a worker takes the job, plus a 45 s allowance for the queue; `plugin_run_deadline.dart`) wraps the run; when it passes the run is cancelled and counts as `network`.
5. The storage map a script finished with is written back with the guarded `setLyricsPluginStorage(..., expectedUpdatedAt)`, so a run that outlived an uninstall or update writes nothing; a run cancelled from outside writes nothing at all.
6. The unregister call runs in `finally`.

**Failure mapping** (`pluginRunFailure`), first match wins:

| Run result | Lookup sees |
|---|---|
| `cancelled` by an update or uninstall of the plugin | `LyricsSourceSkipped` (no failure, no pause, nothing logged): the caller's operation goes on with the other sources |
| `cancelled` because the caller left (the next `fetch` send found the lookup abandoned) | `LyricsRequestAbandoned` (no failure, no backoff, nothing logged) |
| a failed `fetch` of the run, even if the script caught it and returned data | its kind: `network`, `blockedHost`, `notConsented`, `rateLimited` (with `retryAfter`), `invalidRequest` and `invalidResponse` as `invalidResponse`; so a swallowed error is never cached as "no lyrics" |
| `Response.error(msg, {kind, retryAfterSec})` | that kind (`server` by default) |
| `busy` (queue full) | `LyricsSourceSkipped` |
| `timeout` | `network` |
| `memory`, `stack`, `outputTooLarge`, a thrown error without a kind, a bad output shape, and `internal` (a host fault, mapped the same on purpose: the source then pauses instead of being asked again at once) | `invalidResponse` |

**Skipped sources.** A skipped source stores nothing and starts no pause. The automatic lookup would see it as unanswered and start again after every 1 s debounce for as long as the runtime stays busy, so it waits `onlineLyricsSkipRetryProvider` (30 s) before asking again; showing the song again starts a lookup at once. The same holds when the database refuses the row because the plugin was removed while the lookup ran (`saveOnlineLyrics` returns false, the lookup result is `notStored`, not `found`).

**Per-source pause.** `onlineLyricsBackoffProvider` is a map from provider id to the moment its pause ends. A failure pauses only the failing source (60 s minimum, longer for a `Retry-After`, up to 30 % random jitter); automatic lookups skip paused sources and the resolution picks the first enabled source that is not paused. A plugin's `retryAfter` pauses only that plugin. "Clear saved lyrics", Retry and Search again lift every pause.

**Two logging channels.** (1) `<data>/plugin-logs/<installId>.jsonl`, written by `PluginRunLog`: one JSON object per line for each run that failed or printed to the console, `{ts, installId, pluginName, version, script, query, kind, message, stack, console[], requests[{method, host, path, status, ms}]}`. `query` is the run input (song data; the file is local only and never attached to a bug report by itself); `requests[]` is recorded by the fetch bridge (path without query or fragment; a call that hung is listed with `status: null`); `console` and `stack` come from the run result (50 lines of 500 characters at most), and the notes about search items that were dropped as invalid (`result #4: "artist" must be a non-empty string`) are added to `console` with a `dropped: ` prefix. Every config value of four characters or more is replaced by `***` in `message`, `stack`, `console` and the request paths, also in its percent-encoded forms. Writes go through one serial queue per file and are not awaited by the lookup; a file over 512 KiB moves to `.jsonl.1` (so at most about 1 MiB per plugin); a write failure is logged once (type only) and dropped. A run that ended cancelled or skipped is not written. Uninstall calls `PluginRunLog.deleteLogs` inside that queue: writes queued before the delete are dropped, writes queued after it go through, so a revived plugin (same id) logs again with no extra step. (2) The app log gets one INFO line per failed run on `lyrics_plugin`: the plugin's name, `installId`, script, kind, and the host (only) of a blocked address. Never song data, paths, console lines or stacks. Successful runs write nothing there.

**Invariants.**

- Every plugin run is registered in `PluginRunRegistry` before the record or package is read, and unregistered when it ends.
- No row, pin or storage write for a plugin is made after its record is removed (guarded queries); a lookup never reports `found` for a row that was not stored.
- A plugin failure is a `LyricsFetchException`, `LyricsRequestAbandoned` or `LyricsSourceSkipped`; the host never stores "not found" for a failed run.
- Only the declared hosts are reachable, and only through `LyricsHttp`; there is no cookie jar in v1.
