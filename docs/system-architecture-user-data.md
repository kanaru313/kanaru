# System architecture: user data

Part of [System architecture](system-architecture.md).

### User data

Listen history and playlists live in `library.db` beside the scan data, so they are data a scan cannot rebuild. The rules below are the contract for every writer and reader (source: the comments in `user_data_tables.dart`).

| Rule | Detail |
|---|---|
| Path spelling | `path` is the canonical `tracks.path` spelling: absolute, under a symlink-resolved root, no `.` or `..`, bytes as on disk. Writers that start from a track copy `tracks.path`. Player `file://` URIs, M3U import and restored sessions must normalize first. |
| No foreign key to `tracks` | Removing or replacing a root and rescanning delete track rows. `plays`, `play_stats` and `playlist_entries` survive and match again when a file with the same path returns. A moved or renamed file orphans its rows until a re-link exists (not built). |
| Plays are log rows | Rows are inserted or deleted. `path` and `played_at` do not change in normal use; only the recorder sets `listened_ms` of the play it is recording. `listened_ms` is nullable: null means unknown, not 0. |
| Stats kept by triggers | `play_stats` holds the count and first and last `played_at` per path, and a row exists while the path has a play. The triggers `plays_stats_insert`, `plays_stats_delete` and `plays_stats_update` (`listen_history.drift`) keep it equal to a `GROUP BY` over `plays` for every write mode, batch writes and clear-all (`DELETE FROM plays`). Never write `play_stats` from Dart. The triggers are correct only with `PRAGMA recursive_triggers = ON` on every connection that writes `plays` (a REPLACE conflict deletes the old row without firing delete triggers otherwise); `LibraryDatabase.beforeOpen` and the file database setup both set it, together with `foreign_keys`. |
| Writing `plays` | Use drift APIs or `customUpdate(updates: {plays})`, so `.watch()` on `play_stats` refreshes. A bare `customStatement` does not notify watchers. |
| Playlist order | `position` is `0..n-1` per playlist, not unique. Writers renumber inside one transaction; readers order by `position, id`. The same path may appear more than once; each entry's `id` is its identity. |
| Playlist cover | Computed, nothing is stored: the first up to 4 distinct non-null cover keys among the first 64 covered entries by position, looking only at the first 1000 entries (`playlistCollageEntryScanLimit`), so a large playlist without covers does not scan every entry (tracks of one album share a cover, so repeats count once). The playlists page (grid or list) and the playlist page (side pane or header) use the same function (`playlistCollageKeys`). |
| Reset | A library reset deletes roots and tracks, never the file. `make reset-library` runs `packaging/dev/reset-library.sql`: it removes `library_roots`, `tracks`, `track_artists` and `cover_colors` (scan output) and keeps the user-data tables, `excluded_folders` (user configuration) and the translation cache tables `lyric_translations` and `lyric_translation_prefs`. The target refuses a database below schema 6. |

### Listen recording

`ListenRecorder` (`core/stats/`, kept alive from `main.dart`) follows the player state and writes `plays`. A play counts once the track is longer than 30 s and the listening time (`ListenAccumulator`: position deltas while playing, seeks and pauses left out) reaches `ListenThreshold.requiredFor`: the smaller of the share (`listenThresholdPercent`, kept within the length minus 1 s so 100 % is reachable) and the minutes (`listenThresholdMinutes`), the minutes alone when the length is unknown. Defaults 4 min / 50 %. `listenRecorderProvider` listens (does not watch) to the two settings and sets `recorder.threshold`, so a change applies to the playthrough under way from the next player state, without rebuilding the recorder; a row already written stays.

### Listen history reads

`history_queries.dart` (reads) and `history_play_writes.dart` (delete and restore of plays) sit on `LibraryDatabase`. Each read is a one-shot `Future`; the provider layer decides when to run it again.

| Rule | Detail |
|---|---|
| Time bounds | The caller computes every bound from local calendar dates (`DateTime(y, m, d)`, so DST days are 23 or 25 hours) and passes epoch ms as half-open `[start, end)`. SQL never uses `localtime` or `strftime`. Bucket counts take the ascending bounds as one JSON array (`json_each`); empty buckets are dropped, newest first. |
| Indexes | Range counts and the top query search `plays_played_at`; per-track reads and the "Nth listen" subqueries search `plays_path_played` or `plays_played_at`. A test runs `EXPLAIN QUERY PLAN` and fails on a full scan of `plays` under any alias. |
| Order and "Nth listen" | The journal order is `played_at DESC, id DESC`. `nth` is `play_stats.play_count` minus the plays of the same path that come later in `(played_at, id)` order; it is null when the path has no `play_stats` row. |
| Day counts and totals | `historyDayCounts` returns per local day the plays (`count`) and the distinct songs (`tracks`, `count(DISTINCT path)`, so A, B, A is 3 plays and 2 songs); `historyYears` keeps the cheaper plain count. `historyRangeSummary(start, end)` gives `(plays, tracks)` of any range (a year, a Most played window). `historyOverview` gives all plays, songs with a play and the first play from `play_stats`, and up to 4 distinct cover keys from the latest 1000 plays (a bounded subquery with `CROSS JOIN` to `tracks`, so a library without covers is not walked whole). `historyPlayedTracks` lists every played library song by last play, newest first; it reads all of `play_stats`, so it runs only on a button press. EXPLAIN tests cover the day, range and cover SQL. |
| Top | `count DESC`, then the earlier last play inside the range, then `path`; the caller gives the limit. With no range it reads `play_stats` instead of scanning `plays`. |
| Missing tracks | Rows are joined to `tracks` by path with a left join; a path no longer in the library still comes back, with a null track. |
| Delete and restore | `deletePlaysByIds` deletes the plays the user saw (by id, chunks of 500 in one transaction) and returns the rows that existed, newest first; `restorePlays` puts a list back in one transaction. `deletePlay` returns the removed row (or null if it is gone); `restorePlay` inserts it again with the same `id`, safe because `plays.id` is AUTOINCREMENT, and returns false when the id exists. Both go through drift's API, so the `play_stats` triggers and watchers run. A recorder checkpoint that landed while the row was absent is lost, so a restored `listened_ms` can be lower than the real time. |

**Home reads.** `home_queries.dart` (extension `HomeQueries`, SQL in `home_query_sql.dart`) serves the Home page. `homeRecentlyPlayed`, `homeRecentlyAdded`, `homeMemories`, `homeRecentAlbums` and `homeRecentArtists` take `limit`/`offset`; `homeHasTracks` and `homeNewestAddedAt` read the library state and the chips' default window. Tables read: recently played `play_stats` + `tracks`; recently added `tracks`; memories `plays` + `tracks`; recent albums `play_stats` + `tracks`; recent artists `play_stats` + `tracks` + `track_artists`. Every list read joins `tracks` with an inner join, so a track gone from the library is left out (and `homeMemories` joins inside the paged subquery, so the offset does not drift). Order is the latest listen first (`play_stats.last_played_at`), memories by play count then latest play, recently added by `added_at DESC, mtime_ms DESC, id DESC`. No query scans `plays`: memories search the `plays_played_at` range (`played_at` in `[start, end)`). Recently added walks the `tracks_added_at` index from the newest row, the bound written as `added_at >= coalesce(?1, min)`: an `OR` over the parameter hides the range from the planner, which then scans `tracks`. The rest read `play_stats`. The album and artist reads use `CROSS JOIN` so SQLite keeps `play_stats` as the outer loop and searches `tracks` and `track_artists` by index even without `sqlite_stat1`. `play_stats` has no index on `last_played_at`, so the recent lists scan it and sort, which is accepted for the page sizes used (an index would need a schema change). Albums are counted over all their tracks and artists over all their `track_artists` rows, so the numbers match the Albums grid and the Artists tab. The pure windows are in `home_windows.dart`, built from local calendar dates like the history bounds: `memoriesWindow` is the same day last year plus or minus 3 calendar days (half-open; Feb 29 uses Feb 28); `HomeAddedWindow` (1 day, 3 days, 7 days, 30 days, all) and `defaultAddedWindow` drive the chips. A test runs `EXPLAIN QUERY PLAN` on each list query.

**Paging and refresh.** Full lists read `homePageSize` (200) rows per page and load the next page when the end is within one screen; there is no cap. Shelves read `homeShelfLimit` (20) rows. `homeDataVersionProvider` (`home_data_version.dart`) is the one counter every Home provider and full list watches. It goes up on a `plays` change other than the recorder's `listened_ms` checkpoints (debounced 250 ms), on a `tracks` change (the first at once; changes inside `libraryBrowseRefreshIntervalProvider` become one bump at the end of the interval), and when the local day differs from the day of the last read. No timer waits for midnight: `HomeBody` calls `checkDay()` from `AppLifecycleListener.onResume`, so the first look after midnight shows the new day. A full list reloads on a bump by reading its loaded rows again in one query (at least 200 at offset 0) and keeps the old rows until the new ones arrive.

The History page (`features/history/`) reads them as follows.

| Rule | Detail |
|---|---|
| Layout | One fixed-extent list holds every day header line and play of the selected year, so lines are placed without measuring and a flat index finds the day of a line by binary search. Every line is `songCardExtent` tall (`historyLineExtent`, read from the theme and text scale on each build). A header line is a gap with the day bar (`historyDayBarHeight`, at least 48 px) at its bottom, so the bar of day `d` is at offset `start(d) * extent + (extent - bar)` (`barOffsetOfDay`); a calendar jump scrolls there, clamped to the end of the list. The pinned bar is an overlay, not part of the scroll: `stickyAt(offset)` gives the last bar that reached the top and how far the next bar pushes it up (nothing is pinned while the first bar is still in the list). The overlay forwards mouse wheel and touchpad pan-zoom events to the list, since it is opaque and nothing under it is hit. A year is one `HistoryTimelineBody`; a chip or the "Show <year>" line builds a new one. |
| One signal | One subscription to the `plays` table per page. Batches where every update is `UpdateKind.update` (the recorder's `listened_ms` checkpoints) are ignored; an insert, a delete or an update with no kind counts. Changes are collected for 250 ms and then bump one version number that the year and day-count providers watch. |
| Day rows | `HistoryDayRowCache` reads the plays of a day when a line of it is first drawn: at most two reads at once, newest request first, a request nobody renewed for 300 ms is dropped, 40 days kept (least recently used out). A new version marks every day stale but keeps drawing the old rows until the read returns, so rows do not flash. A `tracks` change (a scan) marks them stale at most once per `libraryBrowseRefreshInterval`. |
| Inserts while scrolled | A new play arriving while the list is more than one line from the top is held back and shown when the reader scrolls back near the top or changes year, so nothing moves under them; a day read again meanwhile keeps only as many rows as its header counts (the held plays are the newest rows and are cut). Deletes, restores and a cleared history show at once. There is no scroll anchoring (`jumpTo`). |
| Undo | One snackbar serves every removal. Undo restores every removal made since the snackbar appeared: a removal while it is visible closes it and shows a new one carrying the earlier plays too; while it waits behind another message the plays join it and its title count ("Removed N listens from history") follows. |
| Tap and menu | A tap queues the day's songs, each once at its first place, skipping songs gone from the library (`historyDayTracks`). The player gets only the `tracks` row path, never `plays.path`. Removal is only in the row menu, which keeps the play id it was opened on. |
| Day menu | `runHistoryDayMenu` reads the day's plays when the menu opens, cut to the shown count like a day read while plays are held back, and every action uses that snapshot. Remove calls `deleteMany` with the snapshot's play ids, never a time range, so a play recorded meanwhile survives; the Undo rule above applies. |

The Most played page (`MostPlayedView`, mounted by `MostPlayedScreen` at `/most-played`, in the `HistoryTwoColumnLayout` that History also uses) reads the top query as follows. The pane's totals come from `historyRangeSummary` for the window (the overview for a range that takes in every play), never from the capped list; the filter is `InPageFilterView` over the shown rows.

| Rule | Detail |
|---|---|
| Ranges | `history_range.dart` is pure. Today, 7 days, 30 days (default), 6 months, 1 year, All and Custom, all whole local days ending at midnight after today. 6 months and 1 year are rolling windows of calendar days (`addMonthsClamped`), not calendar years; a calendar year is a Custom range. Period `k` back ends where period `k - 1` starts, so periods tile with no gap or overlap; a Custom range shifts by its own length in days, and Next is off once the range reaches today. |
| Full-history range | A range that takes in the first and the last play (preset or custom) reads the all-time `play_stats` branch: the same answer, cheaper. All reads `play_stats` too. |
| Order and cap | Plays descending, then the earlier last play inside the range, then `path` (done in SQL). At most 500 rows (`historyTopLimit`); the query asks for 501 and the page says "Showing first 500" only when the extra row came back. |
| Playing | A tap queues the songs still in the library in rank order, starting at the tapped one (the index is recomputed after skipping missing ones). Play, Shuffle and the pane menu (Create playlist, Play next, Add to queue) use the same songs, so a missing song is never queued or added; the playlist is named after the range and the page does not open it. |
| Reloading | The provider is a family keyed by the window in epoch ms and watches the one plays version, so a new play or a new range reads again. The page keeps the list it showed and draws a thin progress bar until the read returns. |
| Hidden page | A page in a hidden router branch keeps its state but its providers are paused (`TickerMode(enabled: false)`). A play recorded while Most played is hidden costs no top query, and it reads once when shown again. |
| Picker | `showHistoryRangeDialog` (`history_range_dialog.dart`) is a centred dialog with one month of the `table_calendar` package (Apache-2.0). Bounds are `pickerBounds`: `firstDay = min(first play day, today)`, `lastDay = max(last play day, today)`; the current Custom range is cut to them (dropped when nothing is left), and days outside are off. The package's header is hidden (`headerVisible: false`): it is built from `package:flutter/material.dart` widgets, which do not find the `material_ui` Material, so the dialog draws its own month bar. The package's range mode is off too: the dialog applies its own tap rule (no start, or a complete range: the day starts a new one; a day on or after the start ends it, the same day being a one-day range; an earlier day becomes the start), so the selection lives in the dialog and survives paging. The package hands out UTC midnights; the dialog converts each to a local day (`DateTime(y, m, d)`) before any lookup or return. The Custom chip is off while there is no play. |
| Play-day dots | For the month in view (and the first month, read in `didChangeDependencies` because the page callback does not fire for the first page) the dialog reads which of the 42 days of its six-week grid have a play: `historyPlayDayStarts` over `dayBoundsBetween` (local day starts, DST-safe) with the count-only bucket query. Months are read once and cached in the dialog; a failed read is logged and the dots stay off. |

The song page (`HistoryTrackScreen`, `/history/track?path=`) reads one song's totals and plays as follows.

| Rule | Detail |
|---|---|
| Address | `historyTrackLocation(path)` builds the location with `Uri(path:, queryParameters:)`, so every character of the path is percent-encoded and decoded back unchanged (tests cover `+`, `%`, `#`, `?`, `&`, `=`, spaces, non-ASCII and a 4000-character path). The route lives in `historyRoutes`, a sub-route of the History branch; `app/` is not touched. Opening it uses `context.go`: going back rebuilds `/history` with its tab and range, as the page below stays mounted. |
| One read | `historyTrackProvider` runs `historyTrackSummary` and `historyTrackPlays` in one transaction, so the count in the header and the list agree. It reads again on the shared plays version (insert and delete, not checkpoints) and, at most once per browse interval, after a scan. |
| Path | The query path is only used to look the song up and to name it when it has no library row. The player gets the path of the `tracks` row that matches, never the query string; with no match (an orphan path, `http://…`, a missing or empty parameter) there is no Play button and the player is never called. |
| Removal | Only through the row menu, capturing `plays.id` when it opens, with the same Undo as the journal. Removing every play leaves the page open with "No listens yet". |

### Playlist kinds

`playlists.kind` (invariant 8 in `user_data_tables.dart`): NULL is an ordinary playlist; `'favorites'` is the Favorites playlist, at most one row, enforced by the partial unique index `playlists_favorites_unique`; `'queue'` is a saved queue (constant `queueKind`), may repeat, and is never listed with the playlists. Writers store no other value; readers treat an unknown kind as ordinary. Favorites is created lazily, never seeded: in one transaction, `INSERT OR IGNORE` (drift `InsertMode.insertOrIgnore`) and then `SELECT id FROM playlists WHERE kind = 'favorites'`. `insertReturning` is not used (an ignored insert returns no row) and neither is `DoNothing(target: [kind])` (drift emits no `WHERE`, which SQLite rejects for a partial index). Favorites entries follow the same path, order and no-foreign-key rules as any playlist.

### Scan-side tables

| Table | Rule |
|---|---|
| `cover_colors` | Keyed by `tracks.cover_key`, no foreign key (one key serves many tracks). `seed` is ARGB as an unsigned 32-bit integer; `0` (alpha 0) means the cover has no usable accent color (grey) and the app falls back to the system accent. `palette` matches `^[0-9a-f]{8}(,[0-9a-f]{8}){0,7}$`, most important first; a row that does not match counts as missing. `algo_version` is `revision * 100000 + thumbnail size` (constant owned by the color extraction code); a different value counts as missing. Orphans are removed with `DELETE FROM cover_colors WHERE cover_key NOT IN (SELECT cover_key FROM tracks WHERE cover_key IS NOT NULL)`: without `IS NOT NULL` one NULL `cover_key` makes `NOT IN` delete nothing. |
| `excluded_folders` | Canonical paths like `library_roots.path`, unique, no foreign key to roots (removing or replacing a root keeps its exclusions). Match with `isSameOrInside` (`core/indexer/root_path.dart`), never `LIKE`. |

Paths that come from outside the library (command-line files, M3U lines, restored sessions) must go through `localAudioPath` (`core/paths/local_audio_path.dart`) before they reach the player or these tables: it accepts an absolute path, a `file:` URI (percent-decoded) or a path relative to a given folder, and returns the invariant-1 spelling of an existing regular audio file, or null. Every other `scheme://` (`http`, `edl`, `av`, …) gives null, since mpv would open it. Files opened from the command line or "Open with" go through it (`core/open_files/open_files_service.dart`). It vouches for the file name only; on a case-insensitive mount a differently cased name passes as written. References inside a local file (an EDL or playlist) are limited by the player's mpv options (`demuxer=lavf` with `protocol_whitelist=file`), not by this check.

Planned schema work: collapsing the history to v1 before the first release (PKG-08). See [project-roadmap.md](./project-roadmap.md). Playlists, Favorites and M3U (PL-01 to PL-05) read and write these tables, see [Playlists](#playlists). Listen history (STAT-01, STAT-10 and the History page) uses `plays` and `play_stats`, see [Listen history reads](#listen-history-reads).

### Playlists

Code: `lib/core/database/playlist_queries.dart` (reads, extension `PlaylistQueries`), `playlist_writes.dart` (writes, `PlaylistWrites`), `playlist_page_queries.dart` (the windowed page reads, `PlaylistPageQueries`), `playlist_page_shared.dart` (row mapper and collage read shared by both), `playlist_rows.dart` (row models), `playlist_cover_keys.dart` (collage rule), `playlist_favorites.dart` (the Favorites playlist, `PlaylistFavorites`), `playlist_library_paths.dart` (`libraryPathsAmong`: which of a list of paths are library rows, one `json_each` query), `playlist_providers.dart` (`playlistSummariesProvider`, `favoritePathsProvider`, `favoritesPlaylistIdProvider`); UI in `lib/features/playlists/` and `lib/shared/widgets/add_to_playlist/`. The sidebar's Playlists row is a plain `AppDestination` (`lib/app/shell/app_destination.dart`), not a list of playlists.

| Topic | Rule |
|---|---|
| Writes | Each is one transaction and addresses entries by id, never by position. `movePlaylistEntry` shifts the rows between the old and new place by one in a single `UPDATE`, then sets the entry, which gives the same result as `list.insert(to, list.removeAt(from))`; `to` is clamped; an entry of another playlist throws and changes nothing. `removePlaylistEntries` deletes, then renumbers with one `UPDATE … FROM (ROW_NUMBER())`, and writes nothing when no row matched. Positions stay `0..n-1`. |
| Adding | `addMissingToPlaylist` dedupes the batch (first occurrence wins), drops the paths the playlist already holds, appends the rest and returns `(added, skipped)`, all in one transaction, so two overlapping adds cannot store a path twice. `createPlaylist(paths:)` takes an already deduped batch. Duplicates already stored are left alone. |
| Reactive reads | Lists that do not read `tracks` (`watchPlaylistSummaries`) use `.watch()` on the playlist tables and emit only when the summaries changed, so a reorder or a scan does not wake the add-to-playlist picker (its only app consumer of `playlistSummariesProvider`). Reads that join `tracks` (`playlistPageHead`, `playlistCards`) go through `throttledTracksQuery`, which only sees `tracks` writes, so `playlist_page_data.dart` also listens to the playlist tables and invalidates the provider on every edit: edits show at once, scans stay throttled. Each head load carries a number taken when it starts (`PlaylistHeadLoad.seq`), so the page can ignore a head read before its own writes ended. |
| Page reads | The playlist and Favorites pages never read the whole playlist. `playlistPageHead` reads the summary (name, count), the collage and whether any entry can play, and no entry row. The list has one slot per entry and `PlaylistRowCache` (`lib/features/playlists/`) reads rows 100 at a time by position range (`playlistEntriesAt`, `position >= start AND position < start + 100`, index `playlist_entries_order`) as they come into view, which relies on dense positions (invariant 5). Rows are placed by the position they come back with; a hole shows a placeholder. At most 1200 rows are kept, 2 reads run at once, newest page first, and a page nobody asked for within 300 ms is skipped. Play, Shuffle, the queue menu and M3U export read what they need when used: `playlistPlayableTracks` (playable entries in order, with entry ids) and `playlistPage` (the whole playlist, export only). Measured on 50k entries under load (`flutter test`, `test/core/database/playlist_page_benchmark_test.dart`): opening went from 2 to 4.7 s to under 30 ms, the reread after a reorder from 2.1 to 5.2 s to about 100 ms, and the first row no longer grows with the playlist; a tap reads the queue in 2.4 to 3.1 s (about twice the Songs page). |
| Entries without a track | Page reads left-join `tracks` by path. An entry whose file is not in the library comes back with a null track: it shows as "Not in library", can be moved and removed, and is skipped on play. |
| Reorder in the UI | A drop or a remove changes the cached rows at once (`PlaylistRowCache.move`, `removeAt`) and holds the cache: no page read starts and page results are dropped until every write in flight ended (`PlaylistWriteGate`). Then the head is read again (only heads numbered after the writes are taken) and the rows on screen are read again, so a failed write goes back to what the database holds, with `playlistSaveFailed`. A drop while a write is in flight is ignored; a head that arrives during a drag waits for the drop. The drag bookkeeping (the picked entry, the deferred head, the grace timer after a pointer ends) is the mixin `PlaylistDragTracking` (`playlist_drag_tracking.dart`), used by `PlaylistEntriesView`. Play waits for writes in flight and starts at the tapped entry id (or the next playable entry at or after its index); leaving the page before the queue is read plays nothing. |
| Add flow | Every queue menu ends in `enqueueLoaded` or `enqueueFromDatabase`, which send `QueueAction.addToPlaylist` to `addTracksToPlaylist` instead of `enqueueTracks` (which refuses it). The flow takes the database, messenger, localizations and the root navigator before its first `await`, because the row that opened the menu can be rebuilt away by a rescan while the picker is open; it never reads the caller's `ref` or `context` afterwards. The song modal runs its queue actions with a `QueueHost` captured when it opens (`enqueueLoaded` and the add flow read it from the running zone first), because its footer and Add to playlist run after the modal has closed and the row's `ref` and `context` may be gone by then. |
| Now Playing | The button adds the current track only when its path is a library row (`coverKeyOf`), so no non-canonical path is ever written. |
| Hearts | `NowPlayingFavoriteButton` (Now Playing header and compact page, wide player bar; not the compact bar) reads `favoritePathsProvider`. Liking needs a library row (`coverKeyOf`), like adding to a playlist; unliking does not, so a liked song that left the library can still be taken out. The heart shows the wanted state at once and writes one wanted state at a time, so two quick presses end where they started. The song modal (`openSongModal`) has "Add to / Remove from favorites"; it reads the state from its own stream (`songModalIsFavoriteProvider`), opened with the modal, because the shared favorites stream may be paused when no heart is on screen. Queue rows have one in their menu (right click, long press, menu key: `queue_tile_menu.dart`), with the same rule. Playlist rows (`PlaylistEntryTile`) are `SongTile`s with the heart in the row itself, and the full song menu; a missing-file row (`PlaylistMissingEntryTile`) has a heart only on Favorites, where it has no remove button, so the liked file can still be taken out. |
| Favorites page | `/favorites` (`FavoritesScreen`) shows the Favorites playlist with the same body as `/playlists/:id` (`PlaylistPageBody`, same layout: side pane from 840 px, header below): play, shuffle, reorder, queue menu, and unlike a row through its heart (no remove button). The page shows the localized name (`playlistDisplayName`) and has no rename or delete. Before the first like there is no playlist and the page shows an empty state; an empty playlist shows the favorites empty message. A typed `/playlists/<favorites id>` shows it the same way, without a redirect. |
| M3U files | `lib/core/m3u/`: `readM3uBytes` checks the type first (a FIFO is never opened), then reads through one handle with a 16 MiB cap; `parseM3uBytes` (run in `Isolate.run`) decodes UTF-8 without BOM, or Latin-1 when the bytes are not UTF-8, skips blank and `#` lines, marks lines over 4096 bytes and stops after 50 000 path lines. `importM3uFile` sends every line once through `localAudioPath` with the M3U folder as base (no trimming, no `\` to `/`), 32 lines at a time, merges repeats (first wins) and lists the lines that are not existing local audio files; it can be cancelled between batches. `writeM3u` writes `#EXTM3U`, `#EXTINF` for entries with a library row, then the stored path or a path relative to the target folder (own `relativePath`, no `package:path`); a relative line that starts with `#` or has `:` before its first `/` gets `./`; paths holding a line break or NUL are left out and counted. `exportM3uFile` writes the file a symlink target points to, through a new exclusive temporary file and a rename, with relative lines computed from the real folder. |
| M3U import and export UI | `/playlists` has "Import M3U…" (`m3u_import_flow.dart`): the file picker (`m3uOpenPickerProvider`, M3U types in both cases, MIME types, and "All files": GTK matches patterns case-sensitively), a progress dialog with Cancel, then a new playlist named after the file (extension dropped in any case, control and bidi characters as spaces, at most 100 characters, the default name when empty), which opens. A file with no usable line creates no playlist. Files that exist but are not library songs are kept (they match once their folder is added) and counted. Anything else than a clean import shows a report dialog (first 100 unused lines, each cut to 300 characters). | Save the queue | The queue panel header has "Save queue as playlist" (`lib/features/player/queue/queue_save_flow.dart`): it reads `queue.tracks` once (the order shown, played songs included, the shuffled order when shuffle is on), keeps the local paths that are library rows (`libraryPathsAmong`), first occurrence only, and asks for a name ("Queue" and the date) through `promptAndCreatePlaylist`. | Queue history | Saved queues are playlists with `kind = 'queue'` (`queueKind`). `QueueHistoryRecorder` (`lib/core/queue_history/`, kept alive by `AppShell`) listens to `PlayerService.replacedQueues` (every open or open shuffled that swaps a queue out, and clear queue) and subscribes again when the player rebuilds, like MPRIS follows `seeked`. It turns the old queue into its local paths in play order (`queue.tracks`; queue URIs of local files are already canonical) and leaves it out when it holds the same paths in the same order as the queue playing when the event is heard (tapping another song of the playing album). `recordQueueSnapshot` (`queue_history_writes.dart`) runs in one transaction: fewer than 2 paths writes nothing; the same paths as the newest saved queue only move its `created_at` to now; otherwise a new row and its entries go in with one `INSERT … SELECT FROM json_each(?)` (dense positions) and every saved queue beyond the newest 20 is deleted with its entries (cascade). The paths travel as one JSON array and are compared inside SQLite, so a whole-library queue never comes back to Dart. Writes run one after another; a failure is logged and dropped. Reads: `queueSnapshots` (newest first, count, collage) and `queueSnapshotPaths` (`queue_history_queries.dart`). `/queue-history` (`features/playlists/queue_history_*.dart`) lists them; `/queue-history/:id` shows one with the playlist page body and layout (`PlaylistPageBody`: side pane from 840 px, header below; no rename or delete), named by when it was saved (an id that is not a saved queue shows "not found"); play, shuffle, queue, save as an ordinary playlist (copy through `promptAndCreatePlaylist`) and delete are on the list rows. A typed `/playlists/<saved queue id>` still shows it as a playlist. |
| Favorites | The playlist with `kind = 'favorites'` ([Playlist kinds](#playlist-kinds)). `ensureFavoritesPlaylist` reads the id first and only runs the invariant-8 create (`INSERT OR IGNORE`, then `SELECT id`) when there is none: an ignored insert still tells drift that `playlists` changed, which would reload every open playlist page. `setFavorite(path, favorite:)` sets the wanted state, not a toggle: when it already holds it writes nothing; adding appends at the end (creating the playlist on the first like); removing deletes every entry of that path and renumbers, and never creates the playlist. `renamePlaylist` and `deletePlaylist` filter `kind IS NOT 'favorites'`, so they are no-ops on it (`IS NOT`, not `!=`, which would drop the NULL kind of every ordinary playlist). `watchPlaylistSummaries` and `playlistCards` leave it out, and saved queues too (`kind IS NULL OR kind NOT IN ('favorites', 'queue')`, so ordinary and unknown kinds stay), so the `/playlists` grid and the add-to-playlist picker never list them; `playlistSummary(id)` keeps it and sets `isFavorites`. `favoritePathsProvider` watches only the playlist tables and emits only when the set changes; `isFavorite(path)` reads once, for callers that cannot rely on a live stream (Riverpod pauses a stream with no listener). |
