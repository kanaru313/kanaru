# System architecture: lyrics

Part of [System architecture](system-architecture.md).

### Lyrics

Lyrics are read when a track plays, for the playing track only, and not stored: no column, no slower scan, and a `.lrc` edited outside the app shows at the next play. Translations are stored (schema 8): each translated source line with its translation, in `lyric_translations` (see [section 7](system-architecture-database.md#7-library-database-schema)). Online lyrics results, the per-song choice and pick, and rejected matches have tables too (schema 9; the choice and the rejected text hash came in schema 10, same section); the provider contract, the resolution order and the status are below the table. The order depends on the song's choice: by default (`auto`) local (tags or `.lrc`) > cache > network; `online` puts the song's pick first, and `off` turns the lyrics off (see "Resolution and status").

Online lyrics (provider contract): `core/lyrics/online/` holds a pure layer. A `LyricsProvider` (`id`, `displayName`, `hosts`, `lookup`, `search`, `fetch`) is stateless and async and does no I/O except through the `LyricsHttp` it is given. The host copies its id, name and hosts once into a `LyricsProviderRegistration` (`registerLyricsProviders`, `lyricsProvidersProvider`); later changes of the provider's getters are ignored. Ids must be unique and each host a public DNS name: no IP literal (so no loopback, link-local or private address), single-label or `.localhost`/`.local`/`.internal`/`.lan`/`.home.arpa`/`.localdomain` name, port or path. `LyricsHttp` is the only network capability: `get` (GET, LRCLIB) and `send` (GET or POST for plugin sources; see below), host in the snapshot, `https`, no port or user info (else `blockedHost` before any socket), 10 s connect and 20 s per send, 30 s for the whole call with its busy waits (then `network`, or `rateLimited` with the `Retry-After` of the last 429 or 503 seen), 4 MiB body cap for lyrics (translation: 2 MiB), no redirects (it reuses `sendTranslationRequest`, so a sent request cannot be cancelled), and the app's `User-Agent: Kanaru/<version> (+repository)` is always sent (besides it, `get` sends only `accept: application/json`; `send` forwards the source's allowed headers, with `accept` defaulting to `*/*`); the test-only `LyricsHttp.forTesting` allows `http`, a port and loopback. A 429 or 503 asking for at most 5 s (a 503 without `Retry-After` asks 1 s; a 429 without it is final) is waited out inside `LyricsHttp.get` and sent again, at most twice and one request at a time (at most 10 s added); the last answer is returned as is, so the provider contract is unchanged. `send(LyricsHttpRequest)` (`lyrics_http_request.dart`) shares one loop with `get` (`lyrics_http_send_loop.dart`: abandon, then consent, before every send; retries; the overall timeout; consent withdrawn during the timeout is `notConsented`) and differs in: method `GET` or `POST` with a body (at most 256 KiB, POST only, every byte 0..255) sent as bytes; the source's headers lower-cased, with `user-agent`, `host`, `accept-encoding` (the client keeps its own gzip handling), `connection`, `content-length`, `transfer-encoding`, `te`, `upgrade`, `keep-alive`, `proxy-*`, `trailer` and `expect` dropped silently, the app's `User-Agent` always sent, `accept` defaulting to `*/*` and any other value kept; the answer as raw bytes (at most 4 MiB, no UTF-8 check; charset is decoded by the caller) with status, headers (lower-case, repeated values joined by `, `), url and `sends` (requests made, retries included); and a `deadline` (time the caller has left) that shortens the 30 s overall timeout to the smaller of the two, with no request at all when none is left, and a socket still open at the deadline is closed. `send` takes an `onSend` callback called before each actual send so the caller counts sends even when the call fails. A bad method, header name or value (CR, LF or other control or non-ASCII characters, a name that is not a token) or body throws `LyricsRequestRejected(reason)`, which is not a `LyricsFetchKind` and sends nothing; an over-cap response is still `LyricsFetchException(invalidResponse)`. Both calls go through `sendTranslationRequest`, which takes an optional `bodyBytes` and `decode: false` (raw bytes in `TranslationResponse.bytes`) without changing its translation callers. `abandoned` is asked before every send, the first and each retry included (so an abandoned lookup puts nothing more on the wire); that is the only cancellable point: when every caller of the in-flight lookup has abandoned it by then (an automatic lookup provider is disposed on a song change or when Now Playing closes; a manual lookup never abandons, and a caller that joins the same key's lookup, such as Retry or the song coming back, keeps it going), `LyricsRequestAbandoned` ends the lookup with no failure and no backoff. The automatic backoff (60 s minimum) starts only after those retries fail, and a `rateLimited` failure shows "{provider} is busy. Try again in a moment." instead of "Couldn't reach {provider}". Failures are `LyricsFetchException(kind)` with `retryAfter` (whole seconds clamped to 1 s..15 min; an HTTP date gives none). `LrclibProvider` sends every title, artist and query text in NFC (`nfcText`; LRCLIB finds composed text only, and macOS taggers write decomposed text), and accepts a strict status whitelist: 200 with a JSON body of the expected shape, and 404 whose JSON `name` is `TrackNotFound` (the only "not found"); 429/503 are `rateLimited`, any other status, an HTML 404 from a captive portal or a non-JSON 2xx is an error and never a reason to remember "no lyrics". LRCLIB records are sanitized as they are parsed (C0 controls except newline and tab, DEL and bidi overrides removed; labels at most 512 characters; a lyrics text over 1 MiB in UTF-8 dropped). The host does not rely on that: it checks the output of every provider's `lookup`, `search` and `fetch` (`lyrics_candidate_checks.dart`) before ranking or storing, in `runOnlineLyricsLookup` and in the manual search. A candidate needs a `remoteId` of 1..256 characters without control characters, and a title and artist that are non-empty after trimming and at most 512 characters; an over-long album and a duration outside 0..24 h are dropped; the `providerId` is forced to the registration id. Lyrics texts lose control characters except `\n` and `\t`, `\r\n` becomes `\n`, a text over 1 MiB in UTF-8 is dropped, and synced text that `parseLyricsText` does not read as timed lyrics moves to plain (or is dropped when plain text exists or nothing is left to show). A list keeps at most 20 results, the first of each `remoteId`, and drops an invalid candidate without dropping the list; a non-empty list with no valid candidate is `LyricsFetchException(invalidResponse)`, so a broken source is never cached as "no lyrics". Matching (`lyrics_match.dart`, keys in `lyrics_match_keys.dart`): a candidate passes when the duration differs by at most 3 s, the title is equal, joined-equal or at least 0.85 similar (normalized Levenshtein over code points; `sortKey` fold, `&` as `and`, noise such as `feat.`, `Official Video`, `Remaster`, `Radio Edit` stripped from brackets and ` - ` suffixes, live/remix/acoustic kept), and the artist matches (`lyrics_artist_match.dart`; any artist: the full artist strings are equal, as in `Earth, Wind & Fire`, or any name of the library tag equals or is at least 0.85 similar to any name of the remote string, so `Ngân Ngân, Châu Khải Phong` matches a record by `Chau Khai Phong` whatever the order; the remote string is split on `,` and ` & ` first and then each part on ` x `; a name of one or two code points after folding must be exactly equal; placeholder names such as `Unknown Artist`, `Various Artists`, `Various`, `Nhiều ca sĩ` and `VA` never match), and it has lyrics or is instrumental. The gate has two steps because a two-step source (a plugin) answers its search without lyrics: a record with no body at all passes on its metadata (`LyricsMatch.metadataGood`), its lyrics are fetched with `fetch`, and the fetched text goes through the body checks and the reject-by-text check below before it can be chosen. A record that came with a body (LRCLIB always) is judged as before, and in the ranking a record without a body comes after every good record with one. A candidate whose record is rejected, or whose text hashes like a rejected record (`candidateContentHash`, the same `lyricsContentHash` as translations), never matches. `isAutoSearchable` needs a title, a real first artist and a duration. `/api/get` sends the primary (first) artist; the automatic `/api/search` (after a miss, and the extra search for a plain-only record) sends `track_name` plus `artist_name` (the primary artist) when the tag names exactly one real artist, since LRCLIB matches `artist_name` against any position of a record's artist string and a bare common title fills the 20 results with other songs; a tag with two or more real artists sends `track_name` only, because such a song is often filed under another artist, and the matcher then filters the results by title, duration and any artist. The cache key is sha256 of `v1.k<textKeysVersion>|artist|title|album|seconds`; a song with no title and an artist that is missing or a placeholder such as `Unknown Artist`, `Various Artists`, `VA` or `Nhiều ca sĩ` also appends its track key (path, else uri) as a scope (`LyricsTarget.cacheKey`), so two such songs never share a row.

Consent and the `.lrc` writer: `OnlineLyricsHttpFactory` (`online_lyrics_http_factory.dart`, `onlineLyricsHttpFactoryProvider`) is the only source of a `LyricsHttp`. `forManual(registration)` needs `onlineLyrics.manualConsent`, `forAuto(registration)` the separate `onlineLyrics.autoConsent` (manual consent never implies auto). Consent is global: one answer for every enabled source, not tied to a source or its hosts (the host allowlist in `LyricsHttp` stays, as the security boundary); otherwise it throws `LyricsFetchException(notConsented)` before any socket, so Retry, the dialog and automatic lookup all go through the same check. Consent is read before every send (the first, each retry and a lookup's second request), so withdrawing it stops the next request at once (a request already sent runs to completion, but an answer that arrives after withdrawal is dropped and nothing is stored). A withdrawal during the overall 30 s timeout also ends as `notConsented`, not as a timeout, so it starts no backoff. Settings > Lyrics (`lyrics_setting_rows.dart`) has a row "Online lyrics search permission" (manual, manual and automatic, or not allowed) with a confirmed Withdraw button that calls `withdrawOnlineLyricsConsent()` (both flags and `autoFetch` off in one write); saved lyrics stay, and the next search or the automatic switch shows the notice again. The shared `HttpClient` (`lyricsHttpClientProvider`, 10 s connect timeout, closed with the container) is created only after a request is allowed. `confirmOnlineLyricsNotice(navigator, container, auto:)` (`lib/shared/online_lyrics_notice_dialog.dart`) asks once for all sources and takes no `WidgetRef`: the settings notifier is read from the container before the dialog opens, so the caller may unmount; Continue writes `acknowledgeOnlineLyricsNotice(auto:)` (manual: `manualConsent`; auto: both flags and `autoFetch` in one write); `enableAutoOnlineLyrics()` turns the switch on again when the consent is already kept. `LrcSidecarWriter` (`lrc_write_result.dart` (`LrcWriteResult`, `LrcSidecarWriter`), `lrc_sidecar_writer.dart`, `lrc_sidecar_write_steps.dart`, `lrcSidecarWriterProvider`) is called only by Save lyrics (`OnlineLyricsActions.save`): a pick or an automatic match writes no file. `write(audioPath, body, {replace})` never throws and never deletes. Text: the first of the synced and plain lyrics that `parseLyricsText` accepts (`storedLyricsText`, the rule `parseStoredLyrics` uses, so the file holds what was on screen), `\r\n` to `\n`, one final newline, UTF-8 without BOM, at most 1 MiB; none for instrumental or unparsable text (`nothingToWrite`). Order: the song must be a regular file and both it and its folder, symbolic links resolved, inside a library root and outside every excluded folder (`outsideLibrary`); every existing `<name>.lrc` / `<name>.LRC` is classified without following links; without `replace` an existing entry gives `identical` when the first one holds exactly the new text (read through `readM3uBytes` with the 1 MiB cap, so a FIFO, folder or oversized file is never identical and never blocks) and `exists` otherwise; an entry that is neither a regular file nor a link (a folder, FIFO, socket) gives `trashFailed` before anything moves, also without `replace`, so the user is never asked to confirm a replace that cannot work; stale `.kanaru-lrc-*` folders next to the song older than 10 minutes are removed (best effort, links never followed); the text is written to `lyrics.lrc` inside a private `createTemp('.kanaru-lrc-')` folder (a full disk fails here, before anything is trashed); each classified old file is re-checked and moved to the trash (`.lrc`, then `.LRC`); both names are checked absent again; `rename`. The temp folder is always removed, so no placeholder or partial file is ever visible. A refusal of the trash for the first old file is `trashFailed` (nothing changed); a timeout of the trash for the first old file is `trashTimedOut` (the isolate may still have moved it, so the old file may be in the trash and no new file was written); any failure after a file reached the trash (second trash, a file that reappeared, the rename) is `trashedNotWritten`. A file system error logs only the OS error code and gives `failed`. A gap of well under a millisecond remains between the last check and the rename, where a file made by another program would be replaced. `FileTrash` (`core/native/file_trash.dart`, `fileTrashProvider`) moves a file with GLib's `g_file_trash` through `dart:ffi` inside `Isolate.run`, the caller waiting at most 10 s (`timedOut`; the isolate may still finish). The symbols come from the running process (the Linux runner links GLib), else `libgio-2.0.so.0`; a load failure is `unsupported`. Only the three leading fields of `GError` are read (domain compared with `g_io_error_quark()`, code `NOT_FOUND` gives `notFound`, `NOT_SUPPORTED` gives `unsupported`, anything else `failed`), the error, the `GFile` and the C strings are always freed, and only the code is logged, never a path or message. `OnlineLyricsActions.save(target, origin, {replace})` (`online_lyrics_save_action.dart`) takes the stored text of the record by remote id (pin, else cache), writes it and, on `written` or `identical`, invalidates `playingLocalLyricsProvider` and reads the song's own lyrics again with the current `preferEmbeddedLyrics`: when the result is the `.lrc` with the same content hash the pick is forgotten (the song is `auto`), otherwise the choice stays and the outcome says why (`tagPreferred` when tags won, `otherFile` for a different file such as another `.LRC` spelling). A missing text gives `result: null`. A save is guarded per song: `isSaving(trackKey)` is true while one runs, and a second `save` of the same song is ignored (`result: null`); the UI opens no dialog meanwhile. The UI (`features/player/lyrics/lyrics_save_flow.dart`, `runLyricsSave`) shows the Save lyrics dialog (`.lrc` selected; the tag option disabled, "Coming soon"), confirms replacing by naming every existing file that goes to the trash (`a.lrc and a.LRC` when both exist; found without blocking the UI isolate by `existingLrcSidecars`) and the song's title; it says only that the old file is moved to the trash, on every disk, since GLib picks the trash by device, and tells every result with its own snackbar, partial ones included (a `exists` that comes back after a confirmed replace says another lyrics file just appeared; no record on screen says there are no lyrics to save). It acts on the `LyricsActionRunner` snapshot (`lyrics_action_runner.dart`: container, root navigator, messenger, song and lyrics source, taken once when a menu opens), so a track change during a dialog still saves the song the user saw; the runner logs only the error type.

Manual search: the song menu's Find lyrics online… row (`FindLyricsChoice`; shown by `trackLinkMenuItems(showFindLyrics:)` for any local file, tagged or not, when the row holds a `TrackListItem` or the queue a local `Track`, and the library database is open) is carried out by `TrackMenuRunner` or `QueueRowMenuTarget`, which capture the `ProviderContainer`, the root `NavigatorState` and the `ScaffoldMessengerState` when the menu opens, so a row rebuilt away before the pick changes nothing. `showLyricsPicker` (`lib/shared/lyrics_picker/`) asks the consent notice (Cancel: no dialog, no request), re-reads a library song by path (one cache key for every entry point), opens the Choose lyrics dialog under `UncontrolledProviderScope`, and a pick goes to `OnlineLyricsActions.pick`: the pin in the database, no file, then a snackbar. The source filter is one chip left of the query field (`LyricsPickerSearchRow`, `LyricsPickerSourceMenu`) that opens a dropdown of the sources with results; `lyricsResultSources` and `effectiveSourceFilter` give the dialog and the pane the same sources. The dialog searches on open only for a song with a real title; the prefill leaves out a placeholder artist ("Unknown Artist"), so an artist-only song gets its artist in the field and waits for Search. A song without a real title or artist opens the dialog with an empty query: the results pane shows a note ("Type the artist and title, then press Search") instead of a spinner, Search stays off while the field is blank, and nothing is sent until the user searches (the file name is never prefilled or sent); its cache key is scoped to the track, so rejects stay per song. The pane words a failed search with `lyricsFailureMessage`. The preview shows the start time of each synced line (`mm:ss.xx`, `h:mm:ss.xx` from one hour) in a fixed-width monospace column, with a wrapped line staying under the text; an empty synced line shows its time and a dim note, and plain lyrics show text only. The search state is `lyricsSearchControllerProvider(target)` (per-provider state, ranking, an older search's late results dropped).

Resolution and status (`playing_lyrics_status_provider.dart`, `playing_lyrics_status.dart`, `online_lyrics_resolution.dart`, `lyrics_choice.dart`, `lyrics_source_resolution.dart`, `playing_lyrics_resolution_provider.dart`, `playing_lyrics_source_provider.dart`, `auto_lyrics_lookup_provider.dart`): `playingLyricsStatusProvider` turns the playing track into one `PlayingLyricsStatus` (`null` when nothing plays): `LyricsReading`, `LyricsSearching(providerId)`, `LyricsFound(lyrics, origin?)` or `LyricsNone(reason, origin?)` with reason `noLyrics`, `notFound`, `error`, `off`, `paused` (with `resumeAt`, the end of the automatic pause) or `instrumental`; `OnlineLyricsOrigin` holds provider id, remote id, whether the user pinned it and the length difference. The only statuses a consumer sees are these; nothing else (retry times, request details) is exposed. The song's choice (`LyricsChoice`: `auto`, `local`, `online`, `off`; a null or unknown stored mode reads as `auto`) sets the order. `resolveChoice` (pure, in `online_lyrics_resolution.dart`) is the one place it is written: `off` gives `off` and watches no lookup; `online` gives the pick when it has a usable one; otherwise (`local`, `auto`, or `online` without a usable pick) local lyrics (tags or `.lrc`) win when there are any, else a local file takes the cached answer (found text, instrumental, or a `not_found` younger than 14 days), then an automatic lookup, and other songs get no lyrics. `local` without local lyrics resolves as `auto`, and the effective choice says so. Two lists of sources: `lyricsProvidersProvider` holds the enabled sources in the user's order, which are the ones that run; `lyricsSourceNamesProvider` (`lyrics_source_names.dart`) maps every known provider id to a `LyricsSourceName` (`displayName`, `author?`, `removed`), which is what names a stored row. Today both come from LRCLIB alone. The cache stream (`onlineLyricsCacheProvider`) ignores rows of unknown ids, lists enabled sources first in the user's order, then the other known sources by name, and keeps a row of a known source that is not enabled only when it found lyrics. `lyricsSourcesLoadedProvider` is true once the list is complete: until then the cache stream is loading, a song that needs the cache reads as `LyricsReading` (local lyrics, picks and off still show), and lookups and manual searches wait, so a source still loading is never mistaken for a missing one and nothing is sent on a cold start. A song is "not found" only when every enabled source has a recent `not_found` row (or a found row with no usable text); a miss of a source that is not enabled never counts. An automatic lookup asks only the enabled sources with no row or a stale `not_found`; a manual one asks every enabled source. A fresh failure of one source shows over another source's miss. Resolving never writes. Without a library database, or when the pin, fields or cache cannot be read (logged once), only local lyrics are used and nothing is requested. While the pin, the fresh tag fields or the local read load, the status is `LyricsReading`, or the previous status of the same song so views do not flash. The target (`LyricsTarget`) takes a library song's fields from its database row, not from the queue's older `Track`; a title equal to the file name is no title. Automatic lookups run only while something watches the status (Now Playing is shown), and only when `autoFetch` is on, the automatic consent is accepted, the target is auto-searchable and the session is not in backoff. The watching resolution holds `autoLyricsLookupProvider(target)` (`auto_lyrics_lookup_provider.dart`), which waits the debounce (`onlineLyricsDebounceProvider`, 1 s) before asking the keep-alive `OnlineLyricsLookups` to start: a song skipped within the debounce disposes it and nothing is sent, so ten quick skips send one lookup. A lookup takes `lookup`'s record when it passes the gate; a good match that came without lyrics is fetched in rank order, at most 3 `fetch` calls per lookup, and the first with lyrics (or instrumental) whose text is not a duplicate of a rejected one wins (none: a `not_found` row; a failing `fetch` throws and writes nothing; LRCLIB sends no extra request); a plain-only record (no synced text, not instrumental) also runs `search`, and the best good match replaces it only when that match has synced text (two requests for LRCLIB, three when the best match has to be fetched; a match without a body counts only after its fetch). If that extra search or fetch fails with an error other than withdrawn consent, the plain record is kept (no failure, no backoff); withdrawn consent still ends the lookup. Rejected records, and records whose text hashes like a rejected one, are excluded from the gate and the ranking. Lookups are deduped by cache key, run to completion even if the song changed (a sent request cannot be aborted), write the cache only for whitelisted answers, and a failure sets the in-memory backoff (60 s, or the `Retry-After`, up to 15 min, plus up to 30 % jitter) and no row. The status does not start a lookup from its own cache write: the lookup stays watched until the cache answers. A lookup that ends with nothing recorded (Settings Clear dropped its failure while it ran) restarts the provider after the same debounce, so the song never stays on searching. A song with no local lyrics and no usable cache entry takes its state from the lookup, in this order: running (searching); an automatic lookup due (searching, so an old failure is not shown while a new one is about to run); failed (error); paused with an automatic lookup wanted (`paused`, with `resumeAt`; the pause's end is watched, so an extended pause updates it); otherwise no lyrics. `playingLyricsResolutionProvider` (`playing_lyrics_resolution_provider.dart`, autoDispose) wires the inputs of `resolveChoice` and keeps the whole previous `LyricsSourceResolution` record of the same song (`lyrics_source_resolution.dart`) while the song's own lyrics are read again; `playingLyricsStatusProvider` is a select of its status. `playingLyricsSourceProvider` (`playing_lyrics_source_provider.dart`, autoDispose) gives `chosen`, `effective`, `pin`, `hasLocal` and the status from that same resolution, so no extra database stream is opened per song. `OnlineLyricsLookups.forgetFailures()` drops every remembered failure, and a lookup already running then records no failure and starts no pause; the Settings "Clear" button calls it after a successful clear, together with the backoff's `clear()`. `OnlineLyricsActions` (`online_lyrics_actions.dart`, `onlineLyricsActionsProvider`, usable from a `ProviderContainer`): `retry` clears the backoff and looks up once; `choose` sets the choice (`auto` removes the pin row; `local` and `off` store the choice and keep a stored pick; `online` stores it only when a pick exists; choosing the mode already stored writes nothing; after `auto` or `local`, changed or not, the song's own lyrics are read again); `save` writes the stored lyrics of a record as the song's `.lrc` (see the writer above); `keep` makes an automatic match the pick by its remote id, and does nothing when its text is no longer cached; `reject` (`online_lyrics_reject_action.dart`) remembers the match by id and by the content hash of the lyrics on screen, drops the cached rows with that text and the pick when it is that match (a `local` or `off` choice stays), and sends nothing: automatic resolution runs again; `pick` pins a candidate with its text in the database and writes no file. All requests go through the consent-checked lookups. Rejected matches (and records whose text duplicates one) are hidden only from automatic lookups: the Choose lyrics dialog (`rankCandidates(keepRejected: true)`) lists them last, dimmed and labeled "Rejected", never selects one by itself (the first result that has lyrics or is a good match is selected by itself, and when its fetched text is a rejected one the next such result is selected instead, and so it is when the fetch of an automatic pick finds no lyrics; a result the user clicked stays selected, and so does one whose fetch failed, with its error; at most 3 automatic fetches follow one search, then the selection stays; a result that came without lyrics is selectable, selecting it fetches the lyrics through `LyricsSearchController`, one fetch at a time per result, with a progress indicator in the preview and the usual failure sentence on error; "Use these lyrics" stays off until they are there; a newer search makes the older search and fetches send nothing more, `OnlineLyricsHttpFactory.forManual(abandoned:)`), and picking one pins it and deletes its reject row in the same transaction (`pickOnlineLyrics`). Streams parse stored text once and drop unchanged rows, so the same `Lyrics` instance reaches `LyricsView` across unrelated database writes. The Settings "Saved lyrics" row reads `watchOnlineLyricsStats` and lists only non-zero parts: songs with lyrics (found rows plus picks), their size, songs not found (any stored row that is not a found answer, unknown statuses included), source choices (every pin without a pick, whatever its mode, so a pin is counted once and Clear stays on while any row is stored) and rejected versions; "Nothing saved" when all are zero. Clear deletes all three tables and never touches `.lrc` files. What leaves the machine: title, primary artist (`/api/get`; `/api/search` only for a one-artist tag), rounded duration (`/api/get` only) and, in the manual search, the typed text, plus the `User-Agent`; never paths, file names or device information. Auto lookup with the setting off, without the automatic consent, for a song with local lyrics, without a library, or while Now Playing is closed sends nothing.

Source naming: there is no credit row under the lyrics. The lyrics source button names where they come from: its label ("Auto · LRCLIB", "LRCLIB · Synced", ".lrc file"), and its menu header and tooltip ("Lyrics from LRCLIB · Synced", `lyricsSourceMenuTitle` in `features/player/lyrics/source/lyrics_source_labels.dart`), which is the only place the narrow layout's round icon says it. The translation credit stays on the header translate button. The Choose lyrics dialog is a fixed 840 px wide and scrolls sideways in a narrow window; there is no narrow layout yet. Its height is 85 % of the window up to 720 px with a 440 px floor, below which it scrolls (`lyricsPickerContentHeight`); the result list returns to the top on every search and source filter change.

#### Translation

`lyricsTranslationProvider(appLang)` (`core/lyrics_translation/lyrics_translation_controller.dart`, auto-dispose family; the argument is the app UI language, the default target) turns the playing lyrics, the `lyricsTranslation` settings, the per-song target, the saved rows and the DeepL key into one `LyricsTranslationState`: `Unavailable` (no lyrics for the playing uri, or no library database), `Off` (carries the lyrics hash and target for the menu), `NeedsNotice`, `Loading`, `Ready` (one entry per lyrics line; `fromOtherService` when only the other service has a row), `SameLanguage`, `Failed(kind)`. Only a Now Playing widget that watches it translates: closing Now Playing disposes it, Cover only does not watch it.

Rendering: `LyricsView` watches the state and the display setting and passes `(translations, pending, display, direction)` to `SyncedLyricsView` or `PlainLyricsView`; `TranslatedLineText` (`features/player/lyrics/translation/`) draws a line once for both. Under each line the translation is 0.62x the line size, Replace makes it the main line over the original at 0.5x. The added text has one size and weight in both states and changes only color with the current line, so it never changes height when the current line moves (the main line keeps its own bold switch). `Loading` puts a `LyricsTranslationPlaceholder` bar under every non-blank line; one controller in `LyricsView` pulses all bars through `FadeTransition` in a `RepaintBoundary` each, and it runs only while loading and when animations are allowed. `SyncedLyricsView` puts the current line back at the anchor without a glide when `translations`, `display` or `pending` really change (`listEquals`), unless the user scrolled a moment ago; scrolling code is in the `SyncedLyricsScroll` mixin. `Failed` shows `LyricsTranslationBanner` at the top (reason, "Use <other service>", and Retry except for key, too-long and unsupported-language failures). The lyrics carry no credit: it is on the header translate button. Arabic, Hebrew and Persian translations are set right to left.

- **Order of checks** (`lyrics_translation_derive.dart`): show off, then the notice gate (`noticeAcknowledged` must hold the service; nothing is read or sent before), then the per-song target stream and the saved rows (each still loading is `Loading`, no request), then a running job, the selected service's row, a remembered failure, the other service's row, and last the DeepL key (loading is `Loading`; none is `noKey`; a locked or broken store is `keyStoreLocked` or `keyStoreUnavailable`). Only when a request is needed does the controller arm a 1 s timer (`translationDebounceProvider`); it is the only thing tied to the controller's disposal, because Riverpod runs `onDispose` on every rebuild.
- **Jobs** (`translation_jobs.dart`, keep-alive): keyed by (lyrics hash, target, service); one at a time per key, never cancelled, so a started job finishes and saves its own row even if the song changed (the view only reads the current hash). `run` refuses without a request when the service's notice is not accepted, so Retranslate, Retry and a timer cannot bypass the gate. Lines go out in chunks of 50 lines and 4000 characters; finished chunks are kept for the session, so Retry after a failure sends only the rest. Limits: 1000 unique lines and 20 000 characters (`tooLong`). Lines whose translation is empty or equals the source are dropped; no usable line and a song not in the target language is `emptyResult` and nothing is saved. A song whose dominant detected language is the target is saved as such and shown as a note. A saved row with no lines and another source language reads as missing.
- **Failures** are remembered per key (hash, target, service) until Retry or Retranslate; DeepL failures are also forgotten when the key is saved or removed, after which a request may follow on its own; no provider retries (`retry: (_, _) => null`) and no other automatic resend. An unexpected error logs only its type, never the message.
- **Menu actions**: `retranslate()` forces the selected service and replaces only its row; `retry()`; `useOtherService()` returns false, changing nothing, when the other service's notice is not accepted (the UI shows the notice and then calls `SettingsNotifier.enableTranslation`); `setSongTarget(code)`. Show/hide is `SettingsNotifier.toggleLyricsTranslation`.
- **Header button and menu** (`features/player/lyrics/translation/`): `LyricsTranslationButton` sits after the add-to-playlist button of the wide header (not in Cover only; disabled without lyrics) and is the only header widget that watches the controller. Pressing it opens the menu and never toggles. Off it is a plain icon; on it is `primary` on `surfaceContainerHighest`; loading adds a ring, failed an error dot. With translated lyrics (`Ready`) and room it becomes a pill (`lyrics_translation_pill.dart`): the icon and "<service> · <language>" (the service of the row on screen) on a stadium, the tooltip "Translated by <service> · <language>". The room is `nowPlayingPillLabelRooms` in `now_playing_header_pills.dart`, shared with the lyrics source button: the header width minus every other button (the source button's included), the sleep timer label reserve and the window buttons' divider, split in two only while the translation is a pill (otherwise the source label gets all of it); the label ends with an ellipsis; below `lyricsTranslationMinLabelWidth` (64 px) it stays the round icon. The pill shares the icon's `MenuAnchor`, so an open menu survives the loading to ready switch. Same language: the active icon with the note as tooltip, no pill. The menu (`lyrics_translation_menu.dart`) is built in the button's `build`, so an open menu follows the state: the switch (`T` hint, stays open), the per-song language submenu (`setSongTarget`; Default clears it), display style and service radios (global settings), and a footer (saved, saved from the other service, same language, translating, or the failure reason with Retry). The menu reports open and closed into the header's `floatingOpen` so auto-hide keeps it shown. The narrow layout has an icon-only button after the queue button (`NowPlayingTabs`), always there and disabled while the track has no lyrics. Its menu, like the source menu's, reports into `floatingOpen`, which `NowPlayingTabs` receives from the screen (the narrow header never hides; the flag keeps the keys `L` and `T` out of an open menu).
- **Lyrics source button** (`features/player/lyrics/source/`): `LyricsSourceButton` comes before the translate button (wide header, not in Cover only; narrow tabs header, icon only) and is the only header widget that watches `playingLyricsSourceProvider`. `lyrics_source_labels.dart` (pure) turns the resolution into the label ("Auto · " added when the effective choice is `auto`) and `lyricsSourceMuted`. `NowPlayingHeaderPill` (`now_playing_header_pill.dart`) is the look shared with the translate pill. `lyricsSourceMenuItems` (`lyrics_source_menu.dart`) builds the menu from a `LyricsActionRunner` snapshot taken when the menu opens (container, root navigator, messenger, song, lyrics source), so every item, the Save dialog and the replace confirm act on the song the user saw; the button closes the menu when the playing uri changes. Items call the runner (`choose`, `keep`, `reject`, `findOnline`, `save`), which call `OnlineLyricsActions`. The button registers an "open the menu" callback in a `ValueNotifier` owned by `_NowPlayingScreenState` while it is mounted and clears it on dispose; the `MenuController` stays inside the button, and a key press without a callback or an anchor does nothing. The empty states (`lyrics_status_states.dart`) show the `off` text with "Turn back on" and the `paused` text with `resumeAt` and Retry; `lyricsFailureMessage` (`shared/lyrics_picker/lyrics_failure_message.dart`) words the banner by `LyricsFetchKind`. `LyricsActionRunner.enableAutomatic` shows one snackbar after turning automatic lookup on for a target that is not `isAutoSearchable`.
- **`V` and `L` keys** (`now_playing_screen.dart`): `V` cycles the view mode (wide layout only); `L` calls the source menu callback (both layouts, not in Cover only), focusing the first item. Both use the guards of `T`.
- **`T` key** (`now_playing_screen.dart`, same guards as `V` and `L`, both layouts): plain `T`, `KeyDownEvent`, no modifier, no text field focused, no open popup or menu. Turning off calls `toggleLyricsTranslation`; turning on needs lyrics and goes through `enableTranslationWithNotice`. The network notice (`lib/shared/translation_notice_dialog.dart`) opens when the service is not in `noticeAcknowledged`: Continue writes `enableTranslation(service)` (select, accept, show, one write), Cancel changes nothing. The menu switch, the service radio while translation is on, and the banner's "Use <other>" use the same helpers; the settings screen reuses them.
- **Settings rows** (Settings > Lyrics, `features/settings/lyrics_translation_setting_rows.dart`): the service (while translation is on, a service without an accepted notice goes through `enableTranslationWithNotice`; Cancel keeps the old one), the DeepL key row, the default language (`targetLanguage`, null follows the app) and the saved translations (`translationCacheStatsProvider`, clear through `confirmDestructive`; the per-song language picks stay). The key row is built only while DeepL is chosen, so a Google-only user never makes the app read the key store, and opening Settings sends no request. `DeepLKeyNotifier.save` asks `/v2/usage` first and stores the key only when DeepL accepts it; the dialog stays open with the reason otherwise. The key is never drawn after saving (a mask, the plan from the `:fx` suffix, and the quota read on save and on the refresh icon) and its text field is cleared and disposed with the dialog. Warnings under the row come from `ResolvedSecretStore`: file fallback (with the real path), memory only, and permissions fixed.
- **DeepL key** (`deepl_key_provider.dart`): `deeplApiKeyProvider` reads the secret store only when first watched (DeepL selected). `save` trims the key, checks it with `/v2/usage` and writes it only when DeepL accepts it. `deeplUsageProvider` feeds the settings quota line.
- **Privacy**: lyric lines leave the machine only to the selected service, only after its notice was accepted, and only while a Now Playing widget shows the song. The HTTP client (`translationHttpClientProvider`) is the only network path; tests replace the translators and never reach the network or the keyring.

#### Outgoing requests

Every request the lyrics features can make. The app has no telemetry and sends nothing else for them.

| Host | Used by | Sent | Only when |
|---|---|---|---|
| `lrclib.net` | Online lyrics (`LrclibProvider`) | `/api/get`: title, primary artist, rounded duration. `/api/search`: the title, plus the primary artist when the tag has exactly one real artist (automatic), or the typed text (manual). Never an album. `User-Agent` only | Automatic lookup: Now Playing open, `autoFetch` on, automatic consent given. Manual search: the user searched and accepted the manual notice |
| `translate.googleapis.com` | Lyrics translation (Google) | Lyric lines of the playing song | Google is the chosen service, its notice accepted, a Now Playing widget shows the song |
| `api.deepl.com`, `api-free.deepl.com` (`:fx` keys) | Lyrics translation (DeepL) and key check | Lyric lines; the key in the `Authorization` header (`DeepL-Auth-Key`) | DeepL is the chosen service with its notice accepted. The key is also sent to `/v2/usage` on save and on the refresh icon |

File paths, file names and device information are never sent. The `.lrc` writer and the cache do not use the network.
